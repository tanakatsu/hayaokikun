## Problem Statement

子どもが実際には早起きしたのに打刻を忘れた日、今のアプリには救済手段がない。取り消し（T12）は**今日の記録を「未記録」に戻す**ことしかできず、打ち忘れの日にはそもそも記録がないため何もできない。親がPINで保護された画面から、直近の記録を追加・時刻修正・取り消しできるようにする。

## 過去の決定の見直し

`hayaoki-app.md` は「時刻の書き換えや再打刻は提供しない」と決めていた。理由は、子どもが削除→再打刻すると判定が変わる、正午を過ぎると再打刻できなくなる、の2点。本設計は**子どもの打刻フローには手を入れず**、PINを入れた親だけが**時刻を直接指定**する操作を追加する。そのため、上記の矛盾（時間経過で判定が変わる、再打刻できない時間帯がある）は発生しない。

## Decisions

- **範囲**: 今日＋過去7日（計8日）。未来の日付は対象外。8日以上前の記録は固定のまま。（D1）
- **置き場所**: 設定画面（PINゲートの内側）。`CancelTodaySection` を8行の `RecentEntriesSection` に置き換える。カレンダー画面にはPINの入口を作らない（子どもが使う画面を親向けの操作と混ぜないため）。（D1）
- **修正の印**: Entry に `editedByParent` と `originalPunchedAtLocalTime` を保存する。表示するのは設定画面のリストだけ（「親が修正・元 6:42」など）。カレンダーとToday画面は、通常の達成と同じ見た目にする。（D2）
- **実装方式**: Entry を上書きし、修正の印を付ける（Approach A）。（D4）
- 却下: 修正ログを追記のみで保存する方式（Approach B）。カレンダー・ポイント・ストリーク・保存処理まで変更が広がるうえ、目的（打ち忘れの救済）に対して完全な履歴は不要なため。

## Premises（D3で合意）

1. 以前の「時刻修正・再打刻は提供しない」を見直す。操作できるのはPINを入れた親だけで、子どもの打刻ボタンの仕様は変えない。
2. 対象は今日＋過去7日。目標なし（OFF）の日は一覧に出すが、編集はできない。
3. 操作は「追加（記録なし）」「時刻編集（記録あり）」「取り消し」の3つ。取り消した日も、時刻を編集すれば記録に戻せる（取り消しは元に戻せる操作になる）。
4. 入力できる時刻は打刻の有効時間帯 `MIN_TARGET_TIME`〜`MAX_TARGET_TIME`（現在は 05:00〜08:00、`store/config.ts`）に限る。
5. 達成／遅刻は、その日に有効だった目標時刻と比べて判定し直す。目標時刻は記録の中に固定して保存する。
6. 「親が修正した」ことと、子どもが最初に打刻した時刻を残す。これらの項目がない古いデータもそのまま読めるようにする。

## Recommended Approach（A: Entry を上書きして修正の印を付ける）

### データ（`store/types.ts`）

```ts
export interface Entry {
  // ...既存フィールド
  editedByParent?: boolean;                 // 親が追加・編集した記録なら true
  originalPunchedAtLocalTime?: TimeOfDay;   // 子どもの元の打刻時刻（子どもの打刻を初めて親が編集した時だけ設定し、以降は上書きしない）
}
```

古いデータにはこれらの項目がないので、`undefined` は「修正なし」として扱う。`persistence.ts` の変更は不要。

### ロジック（`store/entries.ts`、純粋関数）

`setEntryTimeByParent(entries, schedule, date, time, today)` を追加する。

- `date` が `today-7`〜`today` の範囲外なら `EntryOutOfEditWindowError` を投げる。
- その日の有効ルールが OFF（または存在しない）なら `NoTargetForDateError` を投げる。
- `time` が有効時間帯の範囲外なら `InvalidEditTimeError` を投げる。秒は `:00` に固定する。
- `date === today` かつ `time` が現在時刻より後なら `InvalidEditTimeError` を投げる（まだ来ていない時刻で当日の達成を先に確定させない。eng review 1A）。関数は `today` の代わりに `now: Date` を受け取り、today と現在時刻をそこから求める。
- **記録なし（追加）**: `targetTimeSnapshot = getEffectiveRule(...).targetTime`、`punchedAtEpochMs` は date＋time のローカル時刻から計算、`editedByParent: true`。
- **記録あり（編集、取り消し済みを含む）**: 既存の `targetTimeSnapshot` は変えない（打刻時点の目標に固定する既存方針のため）。時刻・epoch・status を更新し、`cancelled: false`、`editedByParent: true` にする。`originalPunchedAtLocalTime` は、まだなく、かつ元が子どもの打刻（`editedByParent` でない）の場合だけ設定する。
- status は `computeEntryStatus` で再計算する。

`cancelEntry` に同じ8日間の範囲チェックを加える（今はストアから今日しか渡されないが、渡せる日付が広がるため）。

### 共通化（eng review 3A）

- `store/entries.ts`: `isWithinParentEditWindow(date, today)` を追加し、`cancelEntry` と `setEntryTimeByParent` の両方から使う。範囲の日数は `config.ts` の `PARENT_EDIT_WINDOW_DAYS = 7` に置く。
- `store/useAppStore.ts`: `punchIn`・`cancelEntryAndPersist`・新しいアクションに共通する「保存 → 成功したら set、失敗したら `save-failed`」を、内部ヘルパー `persistEntries(next)` にまとめる。
- `app/settings.tsx`（または `app/components/TimeOfDayField.tsx`）: `ScheduleRow` の時刻入力（ネイティブピッカー、Web の `<input type="time">`、iOS の「完了」ボタン）を `TimeOfDayField` に切り出し、`ScheduleRow` と新しいリストの両方で使う。

### ストア（`store/useAppStore.ts`）

`setEntryTimeByParentAndPersist(date, time)` を追加する。今日の日付と現在時刻は、UIから受け取らずにストアの中で `new Date()` から求める（`addScheduleRuleAndPersist` と同じ）。保存が成功してから state を更新する（楽観的更新はしない）。`LastError` に `'out-of-edit-window' | 'no-target-for-date' | 'invalid-edit-time'` を追加する。

### UI（`app/settings.tsx`）

`RecentEntriesSection`: 今日から7日前まで、新しい順に8行並べる。各行の内容:
- 日付＋曜日、状態（達成／遅刻／未記録／取り消し済み／目標なし）、時刻。修正済みなら「親が修正（元 6:42）」を小さく表示する。
- ボタン: 記録なし・取り消し済みの日は「追加」、記録ありの日は「時刻を変更」と「取り消す」。目標なしの日はボタンを出さない。
- 時刻の入力には、既存のスケジュール設定と同じネイティブのタイムピッカーを使い、範囲は有効時間帯に限る。
- 確認ダイアログ: 取り消しは今と同じ文言に日付を入れる。「元に戻せません」は「時刻を入れ直せば戻せます」に変える。追加・編集は「6/23（火）を 6:25 で記録します（達成）」のように判定結果も表示する。Web版では `window.confirm` にフォールバックする（既存パターンに合わせる）。

### 影響を確認済みの箇所

- カレンダー、ポイント、ストリーク: どれも `entries` から計算するので、変更は不要。修正はすぐに反映される。
- 当日の目標ロック（`isScheduleEditLockedForDate`）: 親が今日の記録を追加すると、今日の目標はロックされる。取り消すとロックが外れる（既存と同じ挙動）。
- 親が今日の記録を先に追加すると、子どもの打刻は `already-punched` になる。これは想定どおりの挙動で、UIの文言は既存のものでよい。
- 励ましメッセージ: `app/today.tsx:33` は描画のたびに全記録からメッセージを再計算する。そのため、親が今日の記録を修正するとメッセージもすぐ変わり、過去の日を修正するとストリーク系のメッセージ（3日・7日連続）も変わる。修正後の記録が事実を表しているので、これを正しい挙動とする（eng review 2A）。

## Success Criteria

- 打ち忘れた昨日の記録を、親が設定画面から 6:20 で追加すると、カレンダーでは達成になり、ポイント・ストリークにも反映される。
- 遅刻の記録を目標以内の時刻に変更すると達成になり、元の時刻が設定画面に表示される。
- 取り消した記録に時刻を入れ直すと、記録が元に戻る。
- 8日前・未来・OFF曜日・時間帯外の時刻は、ストア層で拒否される（UIを通さなくても拒否されることをユニットテストで確認する）。
- 保存に失敗した場合は、UIが変わらずにエラーメッセージが出る。
- `editedByParent` がない既存のデータがそのまま読め、表示も変わらない。
- テスト: `entries.test.ts` と `useAppStore.test.ts` にケースを追加する。Playwright E2E に「追加→カレンダーに反映」のシナリオを1本追加する。

## Open Questions

- 確認ダイアログに「ポイント＋1」などの影響も表示するか（今回は判定結果の表示までとする）。
- 8日という範囲を `config.ts` の定数（`PARENT_EDIT_WINDOW_DAYS = 7`）にするか。家庭ごとに変えたくなった場合の調整用。変更が安いので、定数にすることを推奨する。

## The Assignment

実装の前に、家庭で1回だけ試してほしい。次に子どもが打刻を忘れた朝、**何日目に**気づいたか、**実際に何時に**起きたかを親がどうやって知ったか（本人の申告、自分で見た、など）をメモする。7日という範囲と「時刻を親が入力する」という前提が現実に合っているかを、これで確かめられる。

### データの流れ

```
Settings (PIN解除済み)
  RecentEntriesSection ── 8行: today, today-1 … today-7
     │  行ごと: 状態 / 時刻 / [追加|時刻を変更] [取り消す]
     │  TimeOfDayField（ScheduleRowと共通）
     ▼
useAppStore.setEntryTimeByParentAndPersist(date, time)
     │  now = new Date()（ストアの中で取得）
     ▼
entries.setEntryTimeByParent(entries, schedule, date, time, now)   ← 純粋関数
     │  isWithinParentEditWindow ─✗→ out-of-edit-window
     │  getEffectiveRule OFF/なし ─✗→ no-target-for-date
     │  時間帯外 / 今日で未来の時刻 ─✗→ invalid-edit-time
     │  記録なし → 新規 Entry（snapshot = 有効ルール）
     │  記録あり → 上書き（snapshot維持, cancelled=false, original保存）
     ▼
persistEntries(next) ─ 保存失敗 → save-failed（stateは変えない）
     ▼
entries 更新 → カレンダー / ポイント / ストリーク / 励ましメッセージが再計算される
```

### Failure modes

| 新しいコードパス | 起こりうる失敗 | テスト | エラー処理 | ユーザーに見えるか |
|---|---|---|---|---|
| setEntryTimeByParentAndPersist | AsyncStorage への書き込み失敗 | あり（計画） | save-failed | 表示される |
| 画面を開いたまま日付が変わる | 8行のリストの基準日が古いままになる | ストアで範囲を再チェック | out-of-edit-window | 表示される |
| epoch の計算 | date+time のローカル時刻を UTC として計算する | あり（計画） | — | 表示されない（表示には localTime を使うため影響は小さい） |
| TimeOfDayField の切り出し | Android のダイアログが閉じない、または iOS の「完了」が効かない | 既存 E2E（Web のみ） | — | 実機でのみ発生、目視確認が必要 |

致命的なギャップ（テストもエラー処理もなく、失敗が見えない）: なし。TimeOfDayField のネイティブ挙動は Web の E2E では確認できないため、Expo Go の実機で手動確認する。

### What already exists

- `computeEntryStatus`・`getEffectiveRule`・`addDaysToDateKey`・`isWithinPunchWindow`: そのまま再利用する。
- `cancelEntry` と `cancelEntryAndPersist`: 範囲チェックを足して拡張する。新しく作り直さない。
- `ScheduleRow` の時刻入力: `TimeOfDayField` に切り出して共有する。
- Web 用の `window.confirm`/`window.alert` フォールバック: 同じパターンを使う。

### NOT in scope

- 修正履歴をすべて残すこと（Approach B）: 目的に対して過剰なため、office-hours の D4 で却下。
- カレンダーからの修正: 子どもが使う画面に親向けの操作を混ぜないため、D1 で却下。
- 確認ダイアログにポイントへの影響を表示すること: Open Question に残す。
- 修正時の励ましメッセージの抑制: 2A で不要と判断。

### Parallelization

変更はすべて store/ と app/settings のどちらかに集中し、store の変更が UI の前提になるため、順番に実装する。並列化の余地はない。
